# Browser Chat MCP

Connect an MCP agent to a browser chat that a person opens and approves through an extension. The intended experience uses the person's existing browser login and the chat website itself, not a provider API or exported credentials.

> **Status: early local prototype.** The fixture toolbar-to-MCP read path is manually verified. One explicitly selected disposable Gemini chat also passed read-only toolbar approval, a visible-row snapshot, and later event observations after a prompt sent manually by the user; each grant was disconnected. This is not complete chat history or general Gemini support. There is no message-send tool. Do not use this build to grant access to personal conversations.

## How It Works

An agent requests a connection through MCP. The user selects the local fixture tab and approves the pending request in the extension popup. A browser-spawned Native Messaging host relays bounded observations to a private local broker; only the MCP client that owns the approved connection can read them.

```text
MCP client <-> stdio facade <-> private Unix broker <-> native relay <-> extension <-> approved tab
```

There is no network browser-control listener, unrestricted CDP bridge, model-supplied selector, or provider API key. Approval binds one fixture conversation to its browser tab and document. Reloading the tab, switching the fixture conversation, or restarting the extension invalidates that grant.

## What Works Today

- `chat_request_connection` creates a short-lived pending request; `chat_get_connection` reports owner-visible state and, after approval, a read-only connection ID plus the last snapshot's observation freshness (`not_observed`, `recent`, or `old`). Freshness is not a browser-presence signal.
- `chat_read_messages` requests a **fresh, rendered-only snapshot** through a bounded browser challenge. The broker selects fixture or Gemini from the owned connection, never from model-supplied selectors or URLs. Gemini rows have uncertain identity and unknown completion state; neither provider promises complete chat history.
- `chat_wait_for_events` waits up to 20 seconds for later fixture or Gemini snapshots after an owned cursor, returning at most two per call. Timeouts are explicit; an expired cursor requires another `chat_read_messages` snapshot. A real fixture message and one manually initiated disposable Gemini exchange appeared through this route in separate toolbar tests. After an MV3 worker wake, the extension conservatively expires old fixture and Gemini cursors if an observation gap is possible; Gemini wake/resnapshot was checked only in the synthetic browser. Each event contains the current rendered snapshot, not only newly received rows.
- `chat_prepare_message` creates an immutable **fixture-only** preview for an owned approved connection. Pass its `connectionId`, `expectedGeneration: 1`, the exact `text`, and a new client-generated UUID `idempotencyKey`. It returns an operation ID, `awaiting_approval`, expiry, the exact preview, and a private `recoveryToken`. It does not access the composer, request human approval, or send anything; Gemini handles are refused. Text remains in broker memory for at most 3 minutes, subject to the live connection; private SQLite retains only metadata and ordinary prepared keys for one day after expiry, with a 10,000-record cap. Retrying the same key with changed text/target fails during retention. Internal dispatch-intent keys are never automatically pruned while unresolved.
- `chat_get_operation` reports an owned prepared operation's current state without browser IDs or message text. Optional `draftFill` metadata distinguishes separate fill consent, `filling`, past confirmed readback (`filled` with editor/time), a fixed `failed` code, or `uncertain`. Confirmed readback is not a claim about the current draft or permission to send; it disappears on disconnect/restart. A foreign client's ID is `unknown`; expiry and revocation are explicit. An optional `recoveryToken` from preparation can recover only dispatch metadata (`dispatch_uncertain` or `observed_in_ui`) after restart, never fill state, approval, browser access, or permission to retry. Matching UI evidence is not service acceptance or delivery. Keep this secret private to the MCP client; it is not a review token or an operation ID. The tool cannot approve or dispatch anything.
- On the selected, approved fixture document, the extension popup's **Review fixture drafts** action shows up to eight current exact-text previews. An explicit **Approve draft (no send)** click consumes a one-time review token for that operation and document, producing an in-memory approval lasting at most 2 minutes and capped by the draft's expiry. The panel clears on grant or tab/document changes and at expiry. Page JavaScript and MCP cannot mint approval. Both the isolated popup test and a real installed-toolbar approval passed; neither approval itself edits or submits the draft.
- A separate **Review fixture draft fill** action shows only previously reviewed, still-approved fixture operations. **Allow draft fill (no send)** records a distinct exact-text/document consent using a different one-time token, lasting at most 2 minutes and capped by both draft and ordinary approval expiry. Ordinary no-send approval grants no fill authority. The popup action alone leaves the editor unchanged. The worker checks the active selected fixture grant, fresh preflight, empty editor, and exact readback, never clicking Send. Existing drafts stay intact, consumed attempts (including failed/unanswered ones) cannot be retried, and consent disappears on expiry/revocation/disconnect/restart. A real installed-toolbar test filled the local fixture textarea once, confirmed the two-line draft stayed unsent and the timeline unchanged, then disconnected. Rich-editor coverage remains isolated-test coverage; no real-site write or connector submission is verified or authorized.
- `chat_fill_draft` accepts only the owned fixture `operationId` after that separate popup consent. It consumes consent before one four-second exact-document attempt and returns fixed status/editor/time metadata with `retryAllowed: false`. No text, target, approved flag, or recovery token can be supplied. A known refusal is explicit; lost socket or browser results return `FILL_UNCERTAIN` because the draft may have changed. Never automatically retry or interpret uncertainty as safe to repeat. An earlier call refused before consent does not create an attempt; only a new explicit human consent can authorize a later action. Gemini remains unavailable, and no tool clicks Send.
- `chat_disconnect` lets the owning MCP client revoke a fixture or Gemini grant without closing the tab. The fixture native watcher drops tracking and document observers when its broker grant ends. An unchanged fixture reread refreshes capture time without manufacturing an event.
- The extension observes the approved fixture's message list and publishes bounded updates. Reads are denied for other MCP clients and for revoked or expired grants.
- On a selected saved Gemini chat, the trusted popup can request an explicit read-only grant bound to that tab's exact URL (including a bounded query, if present) and browser document. Fragments remain unsupported; the full URL is not returned to MCP. A real toolbar-approved read returned currently rendered rows labeled `identityQuality: uncertain` and `generationState: unknown`. In a separately authorized trial, the user manually sent one prompt in the same disposable chat and the owner received two later rendered snapshots before disconnecting. This verifies one observed chat shape, not stable row IDs, response completion, or complete history. The popup's structure-only diagnostics and separate draft-input probes do not click Send.

The local toolbar-approval-to-MCP-read route returned two synthetic rows on consecutive reads; switching fixture conversations then made that connection stale and blocked another read. A separate fixture-only message advanced the event cursor and appeared through `chat_wait_for_events`. See [HANDOFF.md](HANDOFF.md) for the exact evidence, remaining risks, and next step.

## Try the Local Fixture

Work inside the supplied devcontainer with Node.js 24+ and Chromium. Its post-create step installs dependencies and builds the packages; for an existing checkout, run:

```bash
npm ci
npm run build
```

Start the fixture and broker in separate terminals, then open the fixture in **container Chromium**:

```bash
npm run dev:fixture
npm run dev:broker
chromium --user-data-dir="$HOME/.local/share/agent-messaging-mcp/chromium-dev" --no-first-run http://127.0.0.1:8787/
```

In `chrome://extensions`, enable Developer Mode and load the unpacked build at `packages/extension/.output/chrome-mv3`. Note its extension ID, then register the exact-origin native host for that browser profile:

```bash
npm run register:native -- --browser chromium --extension-id "$EXTENSION_ID" --user-data-dir "$HOME/.local/share/agent-messaging-mcp/chromium-dev" --preview
npm run register:native -- --browser chromium --extension-id "$EXTENSION_ID" --user-data-dir "$HOME/.local/share/agent-messaging-mcp/chromium-dev"
```

The workspace [MCP configuration](.vscode/mcp.json) registers `browserChatFeasibility` in VS Code. Rebuild and deliberately reload coordinated broker/native/extension builds; restart the MCP server with **MCP: List Servers** so it discovers the current tool set. Call `chat_request_connection`, use the extension's toolbar popup on the selected fixture tab to **View pending requests** and **Approve read-only fixture**, then call `chat_get_connection` with the request ID and `chat_read_messages` with the returned connection ID. Pass the snapshot's cursor and connection ID to `chat_wait_for_events` for later fixture observations. Optionally call `chat_prepare_message` to create a fixture-only preview, use **Review fixture drafts** on that same approved tab to examine the text, and click **Approve draft (no send)** to record temporary approval. For a separate unsent draft edit, use **Review fixture draft fill**, examine that exact text again, and click **Allow draft fill (no send)**; only then call `chat_fill_draft` with its operation ID while the same fixture document remains selected and empty. `chat_get_operation` reports separate fill lifecycle metadata. There is still no commit or submit command. Call `chat_disconnect` when done. A pending request expires after 60 seconds; an approved fixture grant lasts at most five minutes.

## Verification and Limits

```bash
npm run typecheck
npm run test:unit
npm run test:e2e
```

Unit and isolated Chromium tests cover role isolation, native framing, read challenges, event cursors, both providers' worker-wake gap invalidation, Gemini grant selection, fixture-only draft review/approval, and disconnect cleanup; the real toolbar fixture read/event route and a disposable Gemini read/event route also passed manual checks. Automated popup navigation does **not** grant Chrome's `activeTab` permission and is not counted as real-toolbar approval coverage. Read challenges fail closed if the browser cannot verify the approved document. An earlier manually sent Gemini prompt made its grant `stale` before an event returned; a later, separately approved trial delivered two event snapshots. The extension now tolerates a temporarily empty model response and can show only a fixed revocation category in the structure-only popup, but the first failure's exact cause remains unknown. Continuous presence reporting, robust real-site identity/completion semantics, and additional site variants remain open. The opt-in broker and MCP facade can prepare fixture-only text; only the trusted fixture popup can record short-lived approval. An internal, unexposed SQLite dispatch-intent guard persists one unresolved start before any future submit and marks it `unknown` after a restart; abrupt-kill and second-writer tests pass without touching a browser editor. No IPC/MCP/native command can start dispatch, and there is no connector-driven send. Recovery, fresh preflight, and browser submission tests remain required before exposing commit.

The recovery receipt's hash persists in private SQLite; its raw secret is returned only to the preparing MCP client and is absent from native review lists and popup UI. Missing or incorrect secrets reveal no dispatch metadata. An internal fixture reconciler can record a unique new outgoing row matching the exact prepared text, using a fresh approved baseline and continuous observation history. Existing identical rows, ambiguous matches, or gaps stay uncertain. It persists only row ID/time evidence, retains attempted keys, and has no broker/native/MCP command. A private four-second preflight challenge now checks the operation owner, active selected fixture document, empty writable editor, exact text constraints, and unobstructed controls. It returns only readiness or fixed failure codes and cannot edit, click, or authorize a write; there is no public preflight tool. No public tool can start dispatch or submit. The current popup approval explicitly says **no send** and must not be silently repurposed as submit authorization.

The guarded fixture writer uses document-scoped native `insertText` once, preserving multiline Unicode text and the fixture's trusted input model in both editor modes. It consumes a bounded browser attempt ID before input, rechecks after focus, and returns only fixed outcomes. A lost script result after successful editing and an unanswered native completion both produce `FILL_UNCERTAIN`; clearing the draft does not permit replay. Official SDK tests cover public input rejection and owner isolation; an isolated Chromium test calls the public stdio tool through the broker/native/popup path and verifies exact unsent rich-editor text, safe status, replay denial, and disconnect. No durable send intent or outgoing row is created. Real toolbar textarea fill passed; rich-editor fill remains isolated-test coverage. Explicit trusted send-consent UI and crash/lost-response tests around actual submission remain required before any send tool.

The private ledger has a separate fixture-send consent policy gated by successful draft fill, with different tokens from ordinary review and fill consent. Private native/broker send-review listing and approval are authenticated-relay-only; facade callers cannot list or approve, and successful consent creates no dispatch intent. No popup action or public command can issue it or submit. Its expiry cannot be extended by replaying an old review token. Internal journal start now requires that consent, a mandatory post-consent baseline less than four seconds old, and a strict one-shot exact-target/current-draft check. A memory-only authorization can be consumed once only after durable intent; restart, expiry, revocation, changed observations, and UI echoes cannot restore it. The read-only fixture inspector can now check exact prepared text without touching either editor; its default still refuses existing drafts. This primitive is synthetic-tested, not wired to a dispatch-check browser handler or transport. Explicit human send UI, trusted fresh browser checks, browser-side attempt deduplication, and actual-submission crash tests remain prerequisites.
